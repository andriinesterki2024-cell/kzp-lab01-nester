## 2. Мета роботи

Створено консольний Java-застосунок, який читає записи про ремонти з UTF-8 CSV,
перевіряє їх, відкидає хибні рядки з номером і причиною, обчислює показники
варіанта й виводить один звіт у консоль і файл. Налаштовано Maven Wrapper,
JUnit 5, SpotBugs, виконуваний JAR і GitHub Actions на трьох ОС.

## 3. Постановка задачі

Формат запису: `client:String; device:String; diagnosis:String; hours:double; price:double`.

Показники: кількість коректних записів; сумарний час; загальний виторг;
найдовший ремонт (год, клієнт, пристрій).

Перевірки: непорожній рядок; рівно 5 полів; непорожні текстові поля;
`hours > 0`; `price >= 0`; числа скінченні (не NaN/Infinity).

## 4. Структура програми

| Клас | Призначення |
|------|-------------|
| `Main` | аргументи `--help`, `--version`, `--input`, `--output`; коди завершення 0/1/2 |
| `FileReport` | читання/запис UTF-8 через `Path`, створення каталогів |
| `RepairAnalyzer` | перевірка рядків і обчислення показників |

Потік даних: `input.csv` → `readLines` → `analyze` → `RepairSummary` → `format` → консоль + `writeReport`.

## 11. Відповіді на контрольні питання

**1. Яке призначення файла pom.xml?**

Це опис проєкту для Maven: координати (groupId, artifactId, version), версія Java, кодування, залежності й плагіни. За ним Maven визначає, що збирати, які бібліотеки завантажити і які дії виконати на кожній фазі. У моєму проєкті там же задано властивість buildNumber і фільтрацію ресурсів для --version.

**2. Чим відрізняються фази test, verify і package у Maven?**

Фази виконуються у фіксованому порядку, і виклик пізнішої запускає всі попередні. test компілює код і запускає модульні тести. package додатково збирає JAR (у проєкті — ще й shade). verify виконує все попереднє та прив'язані до нього перевірки — тут SpotBugs. Тому `clean verify` перевіряє все: тести, пакування й статичний аналіз.

**3. Навіщо потрібен Maven Wrapper?**

Wrapper (mvnw, mvnw.cmd і .mvn/wrapper) запускає Maven зафіксованої версії без глобальної установки: під час першого запуску він сам завантажує потрібну версію. Завдяки цьому збірка на моєму комп'ютері, у викладача та в GitHub Actions однакова.

**4. Яку роль відіграє метод main?**

Це точка входу: JVM починає виконання з `public static void main(String[] args)`. Через args програма отримує ключі --input, --output, --help, --version. У моєму коді main лише викликає `run` і завершує процес із кодом помилки, а вся логіка винесена в `run`, щоб її можна було тестувати.

**5. Чим примітивний тип відрізняється від String?**

Примітивні типи (int, double, boolean, char, long) зберігають саме значення, не мають методів і не можуть бути null. String — посилальний тип: це незмінний об'єкт з методами (split, strip, isEmpty), змінна містить посилання на нього й може бути null.

**6. Чому середнє потрібно обчислювати в double, навіть якщо сума й кількість мають тип int?**

Ділення двох int у Java цілочислове й відкидає дробову частину: 7 / 2 = 3, а не 3.5. Тому один операнд приводять до double: `(double) total / count`. У моєму варіанті поля hours і price вже мають тип double, тому суми накопичуються в double.

**7. Що станеться, якщо Integer.parseInt отримає рядок "abc"?**

Буде кинуто NumberFormatException. У програмі такий виняток (від Double.parseDouble) перехоплюється в `parseNumber` і перетворюється на повідомлення «Рядок N: поле hours має нечислове значення "два"»; рядок пропускається, а обробка решти файла триває.

**8. Чому не можна мовчки пропускати рядок із помилкою?**

Користувач вважатиме підсумки повними, хоча частину даних не враховано, і не зможе знайти та виправити помилку у файлі. Тому для кожного хибного рядка звіт містить номер і причину, а також загальну кількість пропущених рядків.

**9. Як String.split(";", -1) обробляє порожнє останнє поле?**

Від'ємний ліміт зберігає порожні елементи в кінці: "Іван;Ноутбук;Ремонт;1.0;" дає 5 елементів, останній порожній. Без -1 масив мав би 4 елементи, і порожня ціна виглядала б як неправильна кількість полів, а не як порожнє поле.

**10. Чому для шляхів краще використовувати Path.of, а не "data\\input.csv"?**

Path.of("data", "input.csv") сам підставляє роздільник поточної ОС. Рядок із зворотною косою рискою працює лише у Windows; на Linux і macOS це звичайний символ у назві файла, тож файл не знайдеться.

**11. Навіщо явно задавати StandardCharsets.UTF_8?**

Стандартне кодування залежить від ОС і налаштувань, тож той самий файл може читатися по-різному, а українські літери перетворяться на «кракозябри». Явне UTF-8 при читанні та записі гарантує однакову поведінку на Windows, macOS і Ubuntu.

**12. Чим %n відрізняється від \n у форматованому виводі?**

\n — завжди символ LF. %n у printf / String.format вставляє роздільник рядків поточної ОС: \r\n у Windows і \n у Linux та macOS. Тому звіт має правильні переноси на кожній платформі.

**13. Які дані потрібно перевірити у вашому варіанті?**

Для варіанта 16: рядок непорожній; рівно п'ять полів; client, device, diagnosis непорожні після strip(); hours і price — числа з крапкою; hours > 0; price ≥ 0; обидва значення скінченні (не NaN і не Infinity).

**14. Які тести виявлять помилку в обчисленні середнього?**

Тест на кількох записах із дробовим результатом (сума 7, кількість 2 → 3.5), який зламається при цілочисловому діленні, з порівнянням через похибку `assertEquals(3.5, actual, 0.0001)`; тест на порожній набір, що перевіряє відсутність ділення на нуль. У моєму варіанті середнього немає, аналогічну роль для сум виконують validRecordsAreSummed і invalidLinesDoNotChangeTotals.

**15. Яке призначення статичного аналізатора?**

Він перевіряє код без запуску й знаходить типові дефекти: можливий NullPointerException, незакриті ресурси, відкриття змінюваного внутрішнього стану, неправильні рядки формату. SpotBugs аналізує байт-код у фазі verify; у проєкті зауважень немає.

**16. Яку роль виконує GitHub Actions?**

Автоматично виконує кроки workflow на push і pull_request: на Ubuntu, Windows і macOS збирає проєкт, запускає тести й SpotBugs, пакує JAR, пробно його запускає та публікує як артефакт. Так виявляються помилки, яких не видно на одному комп'ютері.

**17. Що має містити GitHub Issue на дефект?**

Короткий заголовок, кроки відтворення, очікуваний і фактичний результат (поля форми bug.yml), мітку bug. Виправлення пов'язують з Issue через `Closes #N` у PR.

**18. Що Ви повинні вказати у розділі звіту про академічну доброчесність?**

Які інструменти ШІ використано (або що не використано), ролі-агенти та промпти, які рекомендації прийнято, які помилки виправлено, що зроблено самостійно, які джерела використано, і підтвердження відповідальності та розуміння всього поданого коду.

**19. Яку роботу виконує агент DevOps, а яку — агент Валідатор?**

DevOps консультує щодо інфраструктури: pom.xml, Wrapper, SpotBugs, JAR, GitHub Actions, пояснює помилки на різних ОС і складає чек-лист test/verify/package; код предметної області не пише. Валідатор складає перелік крайових випадків, перевіряє результати й оформлює дефекти як Issues; код не виправляє.

**20. Який рядок вашої програми найскладніше пояснити і чому?**

`if (Double.isNaN(value) || Double.isInfinite(value))` у `parseNumber`. Double.parseDouble приймає рядки "NaN" та "Infinity", а будь-яке порівняння з NaN хибне (NaN <= 0.0 дає false), тож перевірка «hours > 0» сама по собі пропустила б NaN, і сумарний час став би NaN. Саме цей дефект оформлено як Issue #7.
