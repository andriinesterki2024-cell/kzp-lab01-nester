## 2. Мета роботи

Заявки зберігаються в параметризованому сховищі `Repository<T>`, експортуються універсальним рефлексивним
`CsvExporter` за анотацією `@CsvColumn`, записуються й читаються через `Path`/`Files` з UTF-8, а відновлені
записи дорівнюють початковим (round-trip). Помилки передаються власним `DataStorageException` із причиною.

## 3. Стан до і після цієї роботи

| | ЛР4 | ЛР5 |
|---|---|---|
| Зберігання | `List<RepairOrder>` у `Main` | `Repository<RepairOrder>`, звіти працюють зі знімком `all()` |
| Експорт | немає | `--export` (CSV + round-trip), `--export-json` (★) |
| Помилки файла | повідомлення CLI | `DataStorageException` з `getCause()` |

## 4. Repository<T>

`add`, `addAll` (null заборонено), `all()` = `List.copyOf` — незмінний знімок, `find(Predicate<? super T>)`, `size()`.
Параметр T перевіряє компілятор: `Repository<RepairOrder>` у `Main`, `Repository<RepairOrderRecord>` в експорті.

## 5. Модель даних

| Поле | Тип | Стовпець | Інваріант |
|------|-----|----------|-----------|
| customer | String | клієнт | не порожнє |
| device | String | пристрій | не порожнє |
| fault | String | несправність | не порожня |
| date | LocalDate | дата | задано |
| cost | double | вартість | скінченна, >= 0 |
| kind | RepairKind (enum) | вид | задано |

`RepairOrderRecord` незмінний; `equals`/`hashCode` порівнюють усі шість полів; `hasKey(customer, date)` — ключ варіанта;
`fromOrder` будує запис із заявки будь-якого підтипу (client → customer, diagnosis → fault, price → cost).

## 6. @CsvColumn

`@Retention(RUNTIME)` (доступна рефлексії під час виконання), `@Target(FIELD)` (лише над полями), `String value()` —
назва стовпця. Порядок стовпців — за Java-іменами полів: cost, customer, date, device, fault, kind.

## 7. Рефлексивний експортер

`AnnotatedFields`: `getDeclaredFields()` класу й предків до Object, фільтр за анотацією, сортування за іменем,
перевірка `trySetAccessible()`; список кешується в `ConcurrentHashMap`. `CsvExporter`: заголовок з анотацій (і для
порожнього списку — тому `Class<T>` окремим параметром), екранування (поле з `,` `"` `\r` `\n` у лапках, лапка
подвоюється), `Files.writeString(UTF_8, CREATE, TRUNCATE_EXISTING, WRITE)`. Експортер не містить назв класів варіанта;
тест `CsvExporterTest` експортує сторонній клас `City extends Place`.

## 16. Відповіді на контрольні питання

**1. Яку проблему розв'язує параметр типу в Repository<T>?**

Один клас сховища придатний для будь-якого типу, а компілятор стежить, щоб у Repository<RepairOrder> потрапляли лише заявки, а в Repository<RepairOrderRecord> — лише записи. Приведення типів (cast) під час читання не потрібні, помилка типу виявляється під час компіляції.

**2. Чим параметризований клас відрізняється від raw type?**

Raw type (Repository без <...>) вимикає перевірку типів: у сховище можна покласти рядок поруч із заявкою, компілятор лише попередить, а ClassCastException виникне під час виконання. Параметризований тип такий код не компілює.

**3. Навіщо Predicate<? super T> у методі пошуку?**

Підстановка ? super T дозволяє передати умову, написану для T або будь-якого його супертипу. У тесті Repository<Integer> приймає Predicate<Number>; так само Predicate<Object> підходить для будь-якого сховища.

**4. Чому all() має повертати незмінний знімок?**

List.copyOf повертає копію, яку не можна змінити: зовнішній код не додасть запис в обхід add (з перевіркою на null), а пізніші додавання до сховища не змінять уже отриманий знімок, з яким працюють запити Stream API.

**5. Що таке checked exception і коли він доречний у цій роботі?**

Це виняток, який компілятор вимагає перехопити або оголосити в throws. DataStorageException — checked, бо помилки файла й формату очікувані й зовнішні: викликач (ExportReport) мусить явно вирішити, що робити, — тут надрукувати повідомлення й причину та продовжити роботу.

**6. Для чого зберігати cause власного винятку?**

Повідомлення описує операцію мовою програми («CSV-запис 2: Некоректне число в полі «вартість»: abc»), а getCause() зберігає першопричину — NumberFormatException, AccessDeniedException тощо. Без причини неможливо з'ясувати, що саме зламалося.

**7. Чим Path і Files кращі за складання шляху рядком?**

Path.of і resolve самі підставляють роздільник ОС (\ у Windows, / у Linux і macOS) і нормалізують шлях; Files дає готові операції з явним кодуванням і режимами відкриття (CREATE, TRUNCATE_EXISTING), а помилки повертає як IOException з точним підтипом.

**8. Чому кодування потрібно задавати і під час запису, і під час читання?**

Кодування за замовчуванням залежить від ОС і налаштувань (у Windows раніше це була cp1251). Якщо записати файл в одному кодуванні, а прочитати в іншому, кирилиця у полях «клієнт» і «пристрій» перетвориться на сміття. Тому і writeString, і readString викликаються з StandardCharsets.UTF_8.

**9. Що роблять @Retention(RUNTIME) і @Target(FIELD)?**

RUNTIME зберігає анотацію в class-файлі й робить її доступною через рефлексію під час виконання (без неї isAnnotationPresent повернув би false). FIELD дозволяє ставити @CsvColumn лише над полями — над методом чи класом буде помилка компіляції.

**10. Чому анотація не виконує експорт сама?**

Анотація — це лише метадані (назва стовпця). Вона не містить коду; дію виконує той, хто її читає, — AnnotatedFields і CsvExporter/JsonExporter.

**11. Чим getDeclaredFields() відрізняється від отримання публічних полів?**

getDeclaredFields() повертає всі поля, оголошені в самому класі, зокрема private, але без успадкованих. getFields() повертає лише public-поля разом з успадкованими. Тому AnnotatedFields викликає getDeclaredFields() для класу та кожного предка до Object.

**12. Навіщо перевіряти trySetAccessible()?**

Поля RepairOrderRecord приватні; перед field.get треба дозволити доступ. trySetAccessible() повертає false, якщо модульна система чи менеджер безпеки забороняють доступ; перевірка дає зрозумілу DataStorageException одразу, а не IllegalAccessException посеред експорту.

**13. Чому порядок полів для CSV потрібно зробити детермінованим?**

JVM не гарантує порядок елементів getDeclaredFields(). Без сортування стовпці могли б помінятися місцями між запусками чи JVM, і файл не прочитався б назад. Поля сортуються за Java-іменами: cost, customer, date, device, fault, kind.

**14. Чому split(",") не підходить для загального CSV?**

Він ділить рядок і по комі всередині лапок: поле "О'Коннор, ""Шон"" мол." розпадеться на два, а лапки залишаться в даних. Крім того, split працює з фізичним рядком, а поле з перенесенням рядка займає кілька рядків. Тому CsvParser — машина станів над усім текстом.

**15. Як екрануються кома, лапка й перенесення рядка в CSV?**

Поле, що містить кому, лапку, \r або \n, береться в подвійні лапки, а кожна лапка всередині подвоюється: О'Коннор, "Шон" мол. → "О'Коннор, ""Шон"" мол.". Інші поля пишуться як є.

**16. Чому порожній список потребує окремого параметра Class<T>?**

Через стирання типів у List<T> під час виконання немає інформації про T, а з порожнього списку не взяти жодного елемента, щоб викликати getClass(). Без Class<T> неможливо побудувати заголовок, тому toCsv(RepairOrderRecord.class, List.of()) повертає рядок заголовка.

**17. Чим універсальний експортер відрізняється від предметного fromCsv?**

Експортеру досить перетворити будь-яке значення на текст (toString), тому він не знає класу. Зворотне перетворення залежить від типу кожного поля (double, LocalDate, RepairKind) та інваріантів, тому його виконує предметний RepairOrderRecord.fromFields.

**18. Які рівні помилок розрізняє програма?**

Модель — інваріанти в конструкторі RepairOrderRecord (IllegalArgumentException); формат — кількість полів, лапки, заголовок; значення — число, дата, тип пристрою (причина — NumberFormatException, DateTimeParseException, IllegalArgumentException); файл — читання й запис (IOException); рефлексія — немає анотованих полів або доступу.

**19. Що доводить тест round-trip?**

Що після запису у файл і читання назад отримано список об'єктів, рівний початковому (equals усіх шести полів, той самий порядок) навіть для коми, лапок, перенесення рядка й кирилиці. Отже, експорт нічого не втрачає й не спотворює, а файл придатний як вхід для наступної програми.

**20. Чому виняток не можна поглинати порожнім catch?**

Програма продовжить працювати з неповними чи хибними даними, ніхто не дізнається про збій, а причину вже не встановити. У проєкті кожен catch або додає контекст і передає причину далі (new DataStorageException(..., e)), або друкує повідомлення й причину користувачеві.

## 17. Висновки

Заявки зберігаються в Repository<T>, експортуються рефлексивно у CSV і JSON та відновлюються без втрат; помилки мають
першопричину. Створений CSV має стабільний заголовок і однозначне екранування, тому може бути вхідними даними для
наступного програмного блоку (Python, ЛР6).
