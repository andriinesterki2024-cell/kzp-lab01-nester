## 2. Мета роботи

Основні циклові обчислення замінено запитами Stream API в класі `RepairQueries`; звіт ЛР1 і поліморфний блок ЛР3
дають ті самі значення.

## 3. Стан до і після цієї роботи

| Цикл (ЛР3) | Stream API (ЛР4) |
|------------|------------------|
| `for` з накопичувачами годин, виторгу й найдовшого (`RepairAnalyzer.summarize`) | `mapToDouble(hours).sum()`, `mapToDouble(price).sum()`, `max(comparingDouble(hours))` |
| `for` + `EnumMap.merge` за видами (`PolymorphicReport`) | `groupingBy(kind, EnumMap, counting())` |
| `for` з накопиченням `finalCost()` | `mapToDouble(RepairOrder::finalCost).sum()` |

Цикл читання рядків файла залишено: він має побічний ефект — повідомлення з номером хибного рядка.

## 4. Контракт даних

Поліморфний тип `RepairOrder` (`WarrantyRepair`, `PaidRepair`). Поля: client, device, diagnosis (несправність), hours,
price (вартість), kind (`RepairKind`), **date** (`LocalDate`), **status** (`RepairStatus`: NEW, IN_PROGRESS, DONE).
CSV: `client;device;diagnosis;hours;price[;kind[;date[;status]]]`; дата ISO, стан `new`/`in_progress`/`done`.
Рядки форматів ЛР1–3 лишаються коректними: вид PAID, дата 2026-01-01, стан DONE (архівні заявки) — тому звіт ЛР1
не змінився. Константи: N = 5; поріг і referenceDate варіант не використовує (фільтр — за станом).

## 5. П'ять запитів

| № | Метод | Джерело → операції → collector | Тип результату |
|---|-------|--------------------------------|----------------|
| 1 | openOrders | orders.stream() → filter(RepairOrder::isOpen) → toList | List<RepairOrder> |
| 2 | devices | → map(RepairOrder::device) → distinct → sorted(Collator uk) → toList | List<String> |
| 3 | costByKind | → collect(groupingBy(kind, EnumMap, summingDouble(price))) | Map<RepairKind, Double> |
| 4 | costStatistics | → collect(summarizingDouble(price)) | DoubleSummaryStatistics |
| 5 | mostExpensive | → sorted(price ↓, date ↑) → limit(N) → toList | List<RepairOrder> |
| — | findByClient | → filter(client) → findFirst | Optional<RepairOrder> |
| ★ | countByKindAndStatus | → groupingBy(kind, EnumMap, groupingBy(status, EnumMap, counting())) | Map<RepairKind, Map<RepairStatus, Long>> |

Сортування пристроїв — український `Collator`: природний порядок String поставив би «Ігрова консоль» після «Холодильника».

## 6. Групування та статистика

Ключ — вид заявки (enum), агрегат — сума вартості; `EnumMap` дає стабільний порядок «гарантійний, платний», види без
заявок відсутні. Статистика: count, min, max, avg, sum; для порожнього входу `count = 0`, а min/max — ±Infinity, тому
звіт друкує «Вартість: немає даних». Числа форматуються з `Locale.ROOT` і двома знаками.

## 7. Компаратор

`Comparator.comparingDouble(RepairOrder::price).reversed().thenComparing(RepairOrder::date)` — вартість за спаданням,
за рівності — дата за зростанням (Андрієнко 2026-01-06 перед Коваль 2026-01-08 за однакових 3200 грн). `reversed()`
застосовано до першого ключа до `thenComparing`. `sorted` іде перед `limit`; N = 0 → порожньо, завеликий N → усі,
від'ємний → `IllegalArgumentException` (і помилка аргументу `--top`).

## 8. Optional

Ключ — ім'я клієнта без урахування регістру й крайових пробілів. Для дубльованого клієнта (Коваль Оксана) повертається
перша заявка в порядку файла; відсутній клієнт — `Optional.empty()`, звіт друкує «не знайдено».

## 15. Відповіді на контрольні питання

**1. Чим потік відрізняється від колекції?**

Колекція зберігає заявки (List<RepairOrder>), а потік лише описує обчислення над джерелом і нічого не зберігає. Потік одноразовий: після кінцевої операції його не можна використати вдруге, тому кожен метод RepairQueries створює новий потік через orders.stream().

**2. Які частини має типовий конвеєр Stream API?**

Джерело (orders.stream()), проміжні операції (filter, map, distinct, sorted, limit) і кінцева операція (toList, collect, findFirst). Наприклад, devices: orders.stream() → map(RepairOrder::device) → distinct() → sorted(collator) → toList().

**3. Чому проміжні операції називають лінивими?**

Вони не виконуються одразу, а лише додають крок до конвеєра й повертають новий потік. Обчислення запускає кінцева операція; завдяки цьому findFirst у findByClient зупиняється на першому знайденому клієнті й не перевіряє решту заявок.

**4. Що робить filter і який тип має його предикат?**

filter залишає елементи, для яких предикат повертає true. Предикат має тип Predicate<? super RepairOrder>; в openOrders це посилання на метод RepairOrder::isOpen, яке залишає заявки зі станом «нова» або «у роботі».

**5. Чим map відрізняється від mapToDouble?**

map перетворює кожен елемент на об'єкт іншого типу й повертає Stream<R> (devices: Stream<String> назв пристроїв). mapToDouble повертає DoubleStream примітивів без пакування в Double і має числові операції sum, max, average — так рахуються сумарні години й виторг у summarize.

**6. Для чого застосовується distinct і від чого залежить його результат?**

distinct прибирає повтори; результат залежить від equals і hashCode елементів. Для рядків пристроїв «Смартфон Samsung» двічі стає одним, а для заявок PolymorphicReport рахує унікальні заявки через equals/hashCode з ЛР3.

**7. Чому порядок sorted().limit(N) відрізняється від limit(N).sorted()?**

sorted().limit(5) спочатку впорядковує всі заявки й бере п'ять найдорожчих. limit(5).sorted() бере перші п'ять рядків файла й лише їх сортує — найдорожчий ремонт із сьомого рядка до результату не потрапив би.

**8. Яку роль виконує кінцева операція?**

Запускає весь конвеєр і повертає результат: toList() — незмінний список, collect(...) — карту чи статистику, findFirst() — Optional. До неї жодна проміжна операція не виконується, після неї потік використати не можна.

**9. Коли застосовується Collectors.joining?**

Коли елементи потрібно зібрати в один рядок із роздільником, префіксом і суфіксом. У StreamReport так формується рядок «За видом і станом: гарантійний={нова:1, у роботі:1}…» без ручного StringBuilder і зайвої коми в кінці.

**10. Як groupingBy будує карту груп?**

Для кожного елемента обчислюється ключ класифікатора (RepairOrder::kind), і елемент додається до групи цього ключа. Тип карти задає фабрика: new EnumMap<>(RepairKind.class) дає порядок ключів за оголошенням enum, а не випадковий порядок HashMap.

**11. Як отримати суму в кожній групі через downstream collector?**

Передати третім аргументом groupingBy другий колектор: groupingBy(RepairOrder::kind, () -> new EnumMap<>(RepairKind.class), Collectors.summingDouble(RepairOrder::price)) повертає Map<RepairKind, Double> із сумою вартості за видом заявки.

**12. Які показники містить DoubleSummaryStatistics?**

Кількість (getCount), суму (getSum), мінімум (getMin), максимум (getMax) і середнє (getAverage). costStatistics на input-lab04.csv дає count=7, min=300.00, max=5400.00, avg=2371.43, sum=16600.00.

**13. Які значення має статистика для порожнього потоку?**

count = 0, sum = 0.0, average = 0.0, а min і max — службові Double.POSITIVE_INFINITY та Double.NEGATIVE_INFINITY. Тому StreamReport перевіряє getCount() == 0 і друкує «Вартість: немає даних».

**14. Як утворюється складений компаратор?**

Від базового компаратора за ключем через ланцюжок методів: Comparator.comparingDouble(RepairOrder::price).reversed().thenComparing(RepairOrder::date). Другий критерій застосовується лише за рівності першого — дві заявки по 3200 грн упорядковуються за датою.

**15. Чому reversed() потрібно застосовувати до окремого ключа до thenComparing?**

reversed() обертає весь компаратор, на якому його викликано. Виклик після thenComparing обернув би й дату, і за однакової вартості пізніша заявка стала б першою. Тому reversed() стоїть одразу після comparingDouble(price).

**16. Яку проблему розв'язує Optional у методі пошуку?**

Явно показує, що заявки клієнта може не бути, і змушує викликача обробити цей випадок замість ризику NullPointerException. findByClient ніколи не повертає null: для відсутнього клієнта — Optional.empty().

**17. Чим відрізняються orElse, orElseThrow і ifPresent?**

orElse повертає значення або запасне (StreamReport: found.map(...).orElse("не знайдено")); orElseThrow повертає значення або кидає виняток, коли відсутність — помилка; ifPresent виконує дію лише за наявності значення й нічого не повертає.

**18. Чому накопичення результату через зовнішній змінний список у forEach небажане?**

Це побічний ефект: код не читається як запит, ламається на паралельному потоці (ArrayList не потокобезпечний) і змішує обчислення з мутацією. Правильно збирати результат кінцевою операцією toList() або collect().

**19. Які властивості мають бути перевірені під час рефакторингу циклу на потік?**

Однакові результати циклу й потоку на контрольному, порожньому й граничних наборах: порядок елементів, суми, кількості, min/max, дублікати, відсутній результат пошуку, limit(0)/limit(N)/завеликий N і незмінність вхідної колекції. Це роблять StreamVsLoopTest і RepairQueriesTest; звіт ЛР1 перевіряє BaselineCompatibilityTest.

**20. За яких умов паралельний потік може бути виправданим?**

Коли даних багато (сотні тисяч елементів), операція на елемент дорога, операції асоціативні й без спільного змінного стану, а джерело добре ділиться (ArrayList, масив). Для кількох заявок parallelStream лише додає накладні витрати, тому в роботі використано послідовні потоки.
